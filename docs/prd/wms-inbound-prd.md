This Mini-PRD is grounded in the Desty × Jurnal WMS flow boards (Lark, Jun 2026): the Inbound PO/receiving/Item-Placement flow and the Inbound–Return Order flow. Acceptance criteria below trace to those diagrams.

# TL;DR

| **What this is** | The Inbound backbone of Mekari WMS: the physical-execution engine for the full Inbound lifecycle (PO/ASN intake → scan-validated receiving + QC → guided Item Placement/putaway → close), plus warehouse transfer-in and returns inbound. Each putaway task emits one GRN→Purchase Delivery 1:1 (PO-sourced) or a standalone Stock Movement (direct); billing tier gates whether costing/JE is produced. |
| --- | --- |
| **Research basis** | The prior PRD review failed on stock accuracy: "Level 2 execution on an incomplete Level 1 base." The Jurnal fulfillment **inbound completion rate is 47.06%** (L3M) versus 88.75% outbound — the inbound receiving leak is the hero problem. Competitor benchmark: Jubelio/Odoo already ship complete Level 2 + a scan-first mobile app. Batch/serial ID is a mandatory enforced field — the substrate for the batch-level costing differentiator. |
| **Proposed solution** | Build the Inbound backbone as a task lifecycle on Cluster C (Mekari ERP), driven by a scan-first mobile/web app, with product/stock/shelf synced in (Desty via B↔C binding). Receiving validates against PO/ASN with QC hold + variance flag; Item Placement is guided putaway with per-slot scan. On each putaway task finish, WMS emits a GRN→Purchase Delivery (or standalone Stock Movement) — WMS posts no JE for WMS-package-only billing. The `stock_movement_webhook` propagates corrections to Desty for oversell prevention. |

**Locked rules used in this doc.** 

**(a) Putaway grouping & merge.** A putaway task may handle **one or more Completed receiving tasks** (operator selects them at putaway creation — same product/bin, or same area). Multiple orders' receiving tasks can be merged into one putaway task to improve the placement walk. Posting still splits per source receiving task (rule d).  

**(b) Inbound:** a single received SKU qty **can** be placed across multiple slots within **one** Item Placement task (loop until "All Stock Placed"). 

**(c) Receiving supports partial receipt (Receive Partially → Save Partially)**; a SKU's ordered qty may be received across multiple receiving tasks. A receiving task is never split across multiple putaway tasks — its received stock is taken into **exactly one** putaway task (many receiving tasks may still be merged into one putaway task, but the reverse split does not occur). This keeps the receiving's putaway-progress status binary: Pending Put-away (no putaway taken) or Completed (its one putaway created).

**(d) Single-poster rule (merge + split-GRN).** Posting fires on **putaway completion**. A putaway task emits **one GRN per source receiving task** it handled — each GRN → one standalone Stock Movement 1:1 (direct). So one putaway task → N GRNs → N PD/SM, where N = number of receiving tasks merged, and **1 SM always maps to exactly 1 receiving document**. Receiving completion posts nothing; stock stays Incoming until putaway. WMS posts no on-hand value or JE for WMS-package-only billing. (WHT JE behaviour is owned by the source PRD + Foundational A12 — see Open Questions.

**(e) Task vs parent vocabulary:** a receiving/putaway **task** runs Open → In Progress → **Completed** (terminal); the **Inbound parent** runs Pending → Open → In Progress → Partially Completed → Completed → **Closed** (terminal). "Closed" is reserved for the parent only. 

**(f) Task binding:** each task is auto-assigned to the user who triggers it and is hard-bound to that user (only they can operate/complete it); a Warehouse Manager can reassign or force-complete a stuck task. This hard-binding (which left tasks unbound). 

**(g) Assisted receiving:** a receiving task carries **no per-task expected qty** — it records received qty only. Expected qty lives on the Inbound; the operator is shown remaining-to-receive per SKU (sourced from the Inbound), and Short/Over is computed at the Inbound level only (C1 AC#8), never as a receiving-task status. Receiving only accepts SKUs that are on the Inbound — a non-matching SKU is rejected at entry and kept outside the system (no Incoming record, no on-hand, no posting). 

**h)** a finished receiving task makes its received stock eligible for putaway; any in-scope putaway operator triggers the putaway and becomes assignee. **A finished receiving task carries a putaway-progress terminal status:**

* on a `skip_putaway=FALSE` warehouse it is **Pending Put-away** while no non-cancelled putaway task exists for it, flipping to **Completed** as soon as a non-cancelled putaway is created against it (Open/In Progress/Completed) — signalling it entered the putaway backlog; it reverts to **Pending Put-away** if every connected putaway is Cancelled.
* On `skip_putaway=TRUE` the receiving goes straight to **Completed**.**(h) Putaway is not auto-created on receiving completion:** a Completed receiving task makes its received stock **eligible** for putaway; any in-scope putaway operator triggers the putaway task and becomes its assignee (receiving PIC and putaway PIC can differ). 

**(i) Incoming state:** stock is in **Incoming** from **Inbound creation** onward (Inbound expected incoming-exemption — no batch/serial/location until worked). Receiving does NOT create the Incoming state; it records received qty against already-Incoming stock. On-Hand/Available conversion (out of Incoming) happens only at putaway completion. 

**(j) QC is an optional module**: a tenant toggle decides whether QC hold is available at all. When OFF, receiving flows straight to putaway-eligible with no hold step. When ON, a receiver may **manually** place a flagged qty on hold; only the held qty is blocked from putaway (partial-qty hold — the clear qty stays putaway-eligible). MVP QC is building-blocks only: manual trigger, partial hold, accept/reject disposition + reason code. No auto-triggering, no per-SKU QC rules, no rework state, no vendor claim (all Phase 2). 

**(k) Integrated Transaction** → WMS I/O: **every** Integrated Transaction (Desty PO, Transfer, Sales Return, sales order or any other external source) is converted into a WMS Inbound or Outbound via the creation API and then runs the **exact same** C1 inbound / outbound lifecycle as any other source. WMS holds **no transaction-operation control** for Integrated Transactions — it does not create, edit, approve, or own the Desty document; it only executes the resulting Inbound/Outbound. The only Desty-specific divergences are a small set of **outbound execution limits** (e.g. single-shipment per Desty order) owned by the Outbound Mini-PRD, not here.
