# [WMS PRD 1.2] WMS Outbound

**Parent:** [\[WMS One Pager\] Mekari WMS](https://jurnal.atlassian.net/wiki/spaces/PD/pages/51199967496)

**Status:** draft

**Scope:** MVP only

**Pic:**

Foundational, Inbound & Outbound Section @jeunifer.nia@mekari.com

Inbound & Outbound Integration to Desty @Felix Huang (Anton W)

This Mini-PRD is grounded in the Desty × Jurnal WMS flow boards (Lark, Jun 2026): the Order Processing (outbound) flow, the Inbound PO/receiving/Item-Placement flow, and the Inbound–Return Order flow. Acceptance criteria below trace to those diagrams. **The outbound task lifecycle in this doc is aligned 1:1 with the Inbound Mini-PRD (1.1) lifecycle style** — same task states, hard-binding, manual-trigger eligibility chain, single-poster discipline, and parent status model (adapted for outbound where source rules require).

# TL;DR

| What this is | The Outbound backbone of Mekari WMS: the physical-execution engine for the full Outbound lifecycle (order handoff → process → scan pick → Match-Order pack → ship/manifest → courier handover → shipped/completed). Built as a **task lifecycle identical in shape to the Inbound backbone**: each task is born Open, auto-assigned and hard-bound to its triggering operator, runs Open → In Progress → Completed (terminal), and the next task in the chain is **not auto-created** — an upstream Completed task makes its output **eligible**, and any in-scope operator manually triggers the next task and becomes its assignee (so picker, packer, and shipper can differ). Stock is **reserved at Outbound creation** (Add Reserved + Deduct Available, at the batch/serial/storage-location level) and only converted to an on-hand deduction at the **ship event** (courier handover completed in the shipping document): on-hand is deducted via one ERP document whose type is **source-conditional** — a **Sales Delivery** for ERP-SO-sourced orders (valued on-hand + JE), or a **Stock Movement** for any other source (Desty / Other / WHT; on-hand deducted, JE per billing tier). Picking and packing post nothing. |
| --- | --- |
| Research basis | The prior PRD review failed on stock accuracy: "Level 2 execution on an incomplete Level 1 base." The Jurnal fulfillment **inbound completion rate is 47.06%** (L3M) versus 88.75% outbound — the inbound receiving leak is the hero problem, but outbound must not regress it. Competitor benchmark: Jubelio/Odoo already ship complete Level 2 + a scan-first mobile app; mobile is table stakes. Batch/serial ID is a mandatory enforced field — the substrate for the batch-level costing differentiator, consumed (lot/batch) at the ship event. |
| --- | --- |
| Proposed solution | Build the Outbound backbone as a task lifecycle on Cluster C (Mekari ERP), driven by a scan-first mobile/web app, with product/stock/shelf synced in (Desty via B↔C binding). Order handoff locks the source and reserves stock (Add Reserved + Deduct Available at batch/serial/storage-location granularity); order processing splits packages (source-gated); picking is scan-validated with a 100% completion gate; packing is Match-Order (scan-validated) and is the **grouping point** (a packing task groups one or more Completed picking tasks into one package, source-gated); shipping creates the shipment, scans packages, prints manifest, and on courier handover fires the single ship event that releases the reservation and deducts on-hand via the source-conditional poster (SO → Sales Delivery + JE; any other source → Stock Movement, JE per billing tier). The `stock_movement_webhook` propagates to Desty for oversell prevention, and a picking-detail webhook corrects reservation batch/serial/location detail when picking pulls a different lot/bin than reserved. |

### Locked rules used in this doc

**(a) Picking is source-agnostic.** The picking step is identical for every source (ERP SO, Desty SO, Desty Transfer Out, Other). Source never changes how a unit is picked — it only sets the downstream flags (b, c) and the ship-event poster (g). No per-source branch exists in picking. (Replaces the old (a) pick/pack grouping, (b) package split by source, and (c) pick steps by source.)

**(b)** `allow_partially_picking` **— WAREHOUSE-level.** Governs whether one order's lines may be split across multiple picking tasks. ON → an order may have multiple picking tasks (split by zone/bin/SKU). OFF → the order's lines are grouped by SKU into one consolidated picking task (no splitting). A warehouse setting, not an order/source attribute. Does NOT forbid recording a short pick — only controls task splitting.

**(c)** `allow_partially_completed` **(partial shipping) — ORDER-level.** Governs whether packing may START on an order not yet fully picked. YES → a Completed picking task can proceed to Create Packing Task even before all the order's SKUs are picked → partial shipment, multiple packages, "Partially Completed" status reachable. NO → an "All SKU picked?" gate applies; packing-task creation is held until the order is fully picked (deliver-in-full, one consolidated package).

**(d) Reservation & stock-state chain (granular at batch/serial/storage-location).** At Outbound creation (Backlog, parent = Pending): Add Reserved + Deduct Available for every ordered SKU at full batch/serial/storage-location detail (never SKU-total only). Stock stays Reserved through picking and packing — on-hand never moves. After a picking task Completes, if the picked batch/serial/storage-location differs from reserved ("Batch/SN/Storage Loc changes?" = Yes) a picking-detail update re-points the reservation (Release previous + Add new) before packing; if No, packing proceeds. At the ship event: Release Reserved + Deduct On-Hand (granular). On cancel (failed pickup before ship): reservation released back to Available — never stranded.

**(e) Task lifecycle & binding (identical to Inbound).** Every outbound task is created Open, auto-assigned and hard-bound to its triggering user, runs Open → In Progress → Completed (terminal). Next task is NOT auto-created — a Completed task makes its output eligible and any in-scope operator triggers the next — **except packing completion, which AUTO-creates the Ready-to-Ship line (shipping task) for the package** (the shipper then acts on it: scan to create shipment). Picker/packer/shipper can differ. "Closed" is order-parent terminal only.

**(f) Packing = one task per order (consolidation point); shipping = one per package.** A packing task groups Completed picking tasks belonging to the SAME order into one package — never spans orders. `allow_partially_completed = TRUE` → an order may have multiple packing tasks/packages over time (partial shipments). FALSE → exactly one packing task and one shipping task after a full pick. Cross-order bulk picks that shared a tote are sorted back into per-order packing tasks.

**(g) Single-poster rule — the ship event = shipment-document Completion; source-conditional document.** Posting fires at exactly one point: when the **shipment document moves to Completed** (receiver proof entered), which simultaneously flips every package in that document to **Shipped**. Courier handover alone (task → Out for Delivery, shipment doc → Open) posts nothing. At shipment-doc Completion, on-hand is deducted by exactly one document, never zero: 

(i) ERP Sales Order → Sales Delivery (releases reservation-equivalent, deducts valued on-hand at lot cost, posts JE); 

(ii) any other source (Desty/Other) → Stock Movement (deducts on-hand; JE per billing tier); 

(iii) WMS-package-only Direct Outbound → Stock Movement, no JE. Picking, packing, courier handover, and label/manifest printing post nothing.

The Stock Movement / Sales Delivery is 1:1 with each shipped package in the completed shipment document.

**(h) Warehouse Transfer (WHT) is NOT JE-neutral when executed through WMS — ERP-full tier only.** Standalone WHT in ERP/ Jurnal = costing-neutral, no JE. A WMS-integrated WHT has Transfer-Out (ship at origin) and Transfer-In (receive at destination) separated in time, and goods can go missing in transit — so it is NOT self-cancelling. On the WHT-full billing tier: WHT-Out posts its own Stock Movement + JE (credit origin inventory, debit goods-in-transit) and WHT-In posts its own Stock Movement + JE (credit goods-in-transit, debit destination inventory) — two separate JEs via a goods-in-transit/clearing-account model, not one netted pair. On WMS-only tier: WHT stays JE-neutral (Stock Movements for qty only, no JE), consistent with the tier-gating in. _**Note: WHT JE behavior is owned by the source PRD**_

**(i) Parent status set is flag-conditional.** Order with `allow_partially_completed = FALSE`: Pending → Open → In Progress → Completed → Closed (Cancelled terminal) — **no Partially Completed** (single shipment). Order with `allow_partially_completed = TRUE`: Pending → Open → In Progress → Partially Completed → Completed → Closed (Cancelled terminal). "Closed" is parent-only; tasks end at "Completed." The flag value alone determines the status set — no source is referenced.

**(j) No outbound over/short variance flag.** Unlike Inbound's Short/Over/Match flag, outbound has no over/short variance status. Over-ship of an unpicked lot is impossible; ERP/Jurnal partial fulfilment is captured by Partially Completed; a short deliver-in-full order is held until fully picked (or cancelled), never short-shipped. Closure outcomes: Completed or Cancelled.

**(k) Every integrated transaction → WMS I/O via the A12 creation API.** An external source's transaction converts into a WMS Inbound or Outbound through the A12 creation API and then runs the standard lifecycle; WMS holds no transaction-operation control over the source document. Which of a source's transaction types map to an outbound (e.g. a sales order, a transfer-out) versus an inbound (e.g. a return, a transfer-in) is part of that source's integration configuration, not a behavior branch in this backbone. The A12 `transaction_source` enum carries the concrete source identities (one of which is Desty) for idempotency and the posting-anchor decision only.

**(l) Picking claim — overlap prevention (whole reserved bin-line).** \[UNCHANGED — keep the existing rule (l).\] A picking task claims whole reserved bin-lines at task creation, not at scan; each bin-line is owned by exactly one picking task (no sub-line split in MVP); auto-assignment by location area is Phase 2.

**(m)** `pack_using_source_label` **— ORDER-level (source-label-gated packing start).** Governs whether the packing task may START before the source (marketplace) shipping label is attached to the order. TRUE → the packing task cannot move Pending → In Progress until the source `shipping_label` is present on the order; when it starts and completes, the packer sticks the **source label** on the package (the WMS-generated shipping label is not used for that package). FALSE → packing may start and complete with a blank source label (existing behavior; the WMS packing/shipping label path applies). The flag is carried from Outbound creation and propagates to the order's packing task(s). It is independent of `allow_partially_completed` (partial-shipping) and `allow_partially_picking` (task splitting) — those govern _how many_ tasks/packages exist; this governs _whether a packing task can start_ without the source label. Under `skip_picking = ON` (D8), where picking is merged into packing, this gate applies to the merged pick-pack task's start. The gate releases automatically when the source label lands via the A7 update write-back — no manual un-gate.
